## 4. Butir B — Riwayat status order

### 4.1 Keputusan

Setiap pembuatan order dan setiap perubahan status menulis **satu baris riwayat dalam pernyataan SQL yang sama** dengan perubahan statusnya. Hasilnya atomik: transisi yang gagal tidak meninggalkan jejak, dan status tidak mungkin berubah tanpa riwayat. Jam memakai `now()` database (satu sumber waktu). Alternatif yang ditolak: trigger database (cakupan terjamin tetapi aktor tersembunyi) dan event sourcing penuh (terlalu besar untuk kebutuhan ini).

### 4.2 Tabel (order_db)

```sql
CREATE TABLE order_status_history (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  order_id    uuid NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
  from_status order_status NULL,              -- NULL hanya untuk baris pertama
  to_status   order_status NOT NULL,
  actor_type  varchar(20) NOT NULL,           -- SYSTEM | CUSTOMER | DRIVER
  actor_id    uuid NULL,
  reason      varchar(100) NULL,              -- mis. NO_DRIVER, LOCATION_ERROR, BACKFILL
  occurred_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX order_status_history_order_idx ON order_status_history (order_id, occurred_at);
```

### 4.3 Menulis riwayat (pola CTE)

Perubahan status (pola ini sudah diuji di Postgres 16: transisi sah menulis tepat satu baris, transisi yang kondisinya gagal mengembalikan 0 baris dan tidak menulis riwayat):

```sql
WITH upd AS (
  UPDATE orders
  SET status = $2::order_status, driver_id = COALESCE($5::uuid, driver_id), updated_at = now()
  WHERE id = $1::uuid AND status = $3::order_status      -- kondisi bersyarat tetap dipertahankan
  RETURNING *
), hist AS (
  INSERT INTO order_status_history (order_id, from_status, to_status, actor_type, actor_id, reason)
  SELECT id, $3::order_status, status, $4, $6::uuid, $7 FROM upd
  RETURNING occurred_at
)
SELECT upd.*, hist.occurred_at FROM upd, hist;
```

Pembuatan order memakai pola yang sama: `INSERT INTO orders ... RETURNING *` di dalam CTE, lalu `INSERT INTO order_status_history ... SELECT id, NULL, status, 'CUSTOMER', customer_id FROM ins`.

Aktor: pembuatan dan pembatalan = `CUSTOMER`; `PICKED_UP` dan `COMPLETED` = `DRIVER`; penugasan driver dan `NO_DRIVER_AVAILABLE` = `SYSTEM` (beri `reason`).

### 4.4 Backfill order lama

Satu baris per order yang sudah ada: `from_status NULL`, `to_status = status`, `actor_type = 'SYSTEM'`, `reason = 'BACKFILL'`, `occurred_at = updated_at`. Jangan menambah nilai enum baru dan memakainya di migrasi yang sama (lihat §5).

### 4.5 Event dan WebSocket

Tambahkan `at` (ISO-8601 UTC) ke event `order.created`, `order.driver_assigned`, `order.status_changed`, dan ke payload `order:status`. Nilainya `occurred_at` dari baris riwayat, **bukan** jam saat event dikirim. Notification dan Gateway tidak menghitung jam sendiri.

### 4.6 API

`GET /orders/:id` menambah:

```json
"history": [
  { "status": "PENDING", "at": "2026-10-09T07:12:03.120Z", "actor": "CUSTOMER" },
  { "status": "DRIVER_ASSIGNED", "at": "2026-10-09T07:12:04.002Z", "actor": "SYSTEM" },
  { "status": "PICKED_UP", "at": "2026-10-09T07:15:41.775Z", "actor": "DRIVER" }
]
```

Urut menaik. `GET /orders` (daftar) tidak memuatnya. Kepemilikan dan error sama seperti detail order. Tidak ada endpoint baru. Perbarui DTO dan contoh Swagger.

### 4.7 UI (didelegasikan ke agent UI)

Timeline di halaman tracking dan detail order: satu kartu bubble per status dengan jam lokal perangkat (`HH:mm`) dan durasi antar tahap ("Menunggu driver 2 mnt", "Perjalanan 17 mnt") dari selisih `at`. Pembaruan real-time memakai `order:status.at`; hindari duplikat berdasarkan pasangan `status` dan `at`.

### 4.8 Catatan

- Simpan UTC (`timestamptz`), tampilkan zona waktu perangkat.
- Tidak ada penghapusan atau retensi di v1.2.
- Durasi antar tahap bisa dihitung di SQL dengan `lag(occurred_at) OVER (ORDER BY occurred_at)` bila nanti dibutuhkan untuk analitik.

## 5. Butir C — Pembatalan order oleh customer (opsional)

| Status saat ini | Boleh dibatalkan customer? |
|---|---|
| `PENDING` | ya |
| `DRIVER_ASSIGNED` | ya (driver dilepas) |
| `PICKED_UP`, `COMPLETED`, `NO_DRIVER_AVAILABLE`, `CANCELLED` | tidak (409 `INVALID_STATUS_TRANSITION`) |

- **API:** `POST /orders/:id/cancel` (role `CUSTOMER`, hanya pemilik order, selain itu 403), respons 200 berisi order. Swagger lengkap.
- **State machine:** tambah status `CANCELLED` dan transisi `PENDING → CANCELLED`, `DRIVER_ASSIGNED → CANCELLED`. Update bersyarat (`WHERE status = ...`) yang sudah ada menyelesaikan balapan dengan `PATCH` driver: hanya satu yang menang, yang lain mendapat 409.
- **Efek:** lepaskan driver (best-effort seperti `COMPLETED`, log `warn` bila gagal), tulis riwayat (aktor `CUSTOMER`, `reason = 'CUSTOMER_CANCEL'`), kirim `order.status_changed` ke Notification dan Gateway (driver menerima lewat room user).
- **Migrasi:** `ALTER TYPE order_status ADD VALUE 'CANCELLED'` di migrasi tersendiri. Di Postgres 16 perintah ini boleh di dalam transaksi (seperti migrasi TypeORM), tetapi nilai barunya **tidak boleh dipakai di transaksi yang sama** (sudah dicoba: galat "New enum values must be committed before they can be used").
- **UI:** tombol "Batalkan pesanan" dengan konfirmasi pada status `PENDING` dan `DRIVER_ASSIGNED`; kartu "Dibatalkan" berwarna netral abu-abu di timeline; di sisi driver order hilang disertai toast "Order dibatalkan customer".

## 6. Acceptance Criteria (lanjutan dari AC-24)

**Butir B**
- **AC-25:** Pembuatan order menulis baris riwayat `NULL → PENDING`; setiap transisi sukses menulis tepat satu baris `from → to` dengan `occurred_at`; transisi yang ditolak (403/409) atau gagal tidak menulis baris.
- **AC-26:** Perubahan status dan baris riwayatnya atomik: dua update konkuren dari status yang sama menghasilkan tepat satu perubahan dan satu baris riwayat (dibuktikan tes integrasi DB).
- **AC-27:** `GET /orders/:id` memuat `history` berurutan menaik (`status`, `at`, `actor`); `GET /orders` tidak memuatnya; order lama punya satu baris backfill.
- **AC-28:** Event `order.*` dan `order:status` memuat `at` yang sama persis dengan `occurred_at` pada riwayat.
- **AC-29:** UI menampilkan timeline dengan jam lokal dan durasi antar tahap pada tracking dan detail, termasuk pembaruan real-time.

**Butir C (bila dikerjakan)**
- **AC-30:** `POST /orders/:id/cancel` oleh customer pemilik mengubah `PENDING` atau `DRIVER_ASSIGNED` menjadi `CANCELLED`, melepas driver (bila ada), menulis riwayat (aktor `CUSTOMER`), dan mengirim event.
- **AC-31:** Pembatalan dari status lain atau oleh bukan pemilik ditolak (409 atau 403); `cancel` dan `PICKED_UP` yang bersamaan menghasilkan tepat satu pemenang.
- **AC-32:** UI menampilkan tombol batal sesuai status, dan driver menerima pemberitahuan pembatalan.

### ADR-023 — Riwayat status ditulis dalam statement yang sama dengan perubahan status

**Konteks:** UI membutuhkan jam tiap tahap order, dan audit membutuhkan jejak yang tidak bisa terputus dari perubahan statusnya.
**Keputusan:** tabel `order_status_history`, ditulis lewat CTE bersama `UPDATE`/`INSERT` order; jam dari `now()` database dan diteruskan sebagai `at` pada event dan WebSocket.
**Alternatif ditolak:** trigger database (aktor tersembunyi, sulit diuji dari aplikasi), event sourcing penuh (berlebihan), jam dari saat event dikirim (bisa berbeda dari kenyataan dan tidak terjamin urutannya).
**Konsekuensi:** semua jalur perubahan status wajib lewat repository yang menulis riwayat; satu tambahan tabel kecil; migrasi backfill untuk order lama.
